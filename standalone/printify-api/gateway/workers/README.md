# Protected GET gateway Workers target

This is an undeployed ES module and Durable Object adapter, exercised with Node 24.19 and a PHP 8.4.27 fixture bridge to the exact packaged contracts. It requires Workers Web APIs, a SQLite-backed Durable Object supporting storage transactions, and private service bindings. No npm runtime dependencies. The PHP bridge and file-backed sequencer are local test harnesses. Neither qualifies Cloudflare runtime behavior.

## Trust and ordering

The public Worker returns 404. The Durable Object accepts only the explicit offline-fixture mode. The template sets held mode. A future private ingress must authenticate WordPress instance and current operator session before issuing a short-lived signed grant. The exact request and grant bind operation, selector, account, shop, integration, actor, session and profile revision. Quota uses a stable site/account/shop/integration digest. No operator setting controls the gate.

- CONTRACTS verifies the full typed request and Ed25519 grant, returning exact digests and path. It projects bounded JSON through the reviewed endpoint-specific validators. The Worker independently reconstructs the fixed Printify HTTPS route and checks it before handoff. Provider URLs and continuation links from responses are unused.
- POLICY returns the current independent epoch, sequence, release state, revocations and policy revision. After the local transaction consumes the grant and charges quota, the policy service must atomically compare/advance the independent floor with STOP and revocation checks and bind the returned checkpoint to the exact request, scope and grant. If either write or acknowledgment is uncertain, deny and preserve the discrepancy. Before returning observations, the service must confirm that release is still permitted. A policy transition after admission may suppress release while the admitted read is in flight. Cloudflare storage alone cannot prove rollback resistance.
- FIXTURE_CUSTODY receives only a fixed HTTPS GET, exact account/shop/integration and opaque custody reference, body and time limits, and admission identity. The fixture binding returns synthetic responses. A future production custody service must independently validate admission, use the least-privilege credential, reject redirects, verify TLS, honor egress and size/time controls, and preserve redacted audit evidence. No credentials or direct Internet fetch exist in this module. It never sends a raw provider body to WordPress.
- REPLY_SIGNER signs the same correlated v1 reply reviewed by the standalone verifier. Its dedicated key must stay outside WordPress. Policy, custody and signing trust are deployment prerequisites, not additional roles delegated to the plugin.

## Minimal setup after separate authorization

Allocate one admission object per approved stable scope. Provide a reviewed process to initialize its head against the external epoch and floor, with no auto-init on missing or mismatched state. Initialize a reviewed quota and controlled epoch transition policy. The adapter currently admits at most 100 reads per initialized epoch and retains consumed grant identities until a separately authorized epoch transition. Select independently governed policy/floor, custody, typed-contract and signer services and provide binding identities without adding secrets to this template. Confirm account entitlement, private routes, observability and spend boundaries. Qualify runtime, STOP/drain, revocation, outage, acknowledged and ambiguous restores, and exact WordPress coexistence before proposing a read-only pilot. Preserve current holds and exclude mutations.

`node --test --test-isolation=none standalone/printify-api/gateway/workers/worker.test.mjs` runs the adapter unit checks. Set `DF_PROTECTED_GET_WORKERS_FIXTURE=1` when running the existing disposable `protected-get-wordpress.php` harness to exercise the same ten WordPress read flows through the Workers-target module. The runner uses a single process per interaction and an independent synthetic floor file. It is not a multi-host emulator.

## Binding readiness and signing failures

Before consuming a grant, the admission adapter requires every private binding to expose POST /ready and return a bounded JSON object with ready=true and protocol=DF_STANDALONE_GET_1. This endpoint must be side-effect-free and reflect dependency health, including the signer key being loaded. A failed or unavailable probe returns a generic unavailable response. Each call and response body is subject to the adapter's five-second deadline. Readiness is point-in-time. A later signer failure releases no data and leaves the grant consumed. A policy recheck after signing catches revocation during signing before the Worker releases the reply. Hosted network delivery and an external policy transition are separate trust boundaries and still require qualified drain semantics.

The Hostinger ingress class implements a private, harness-only HTTPS handoff. It requires a separately authenticated instance and a positive binding to the exact site, operator, session, profile revision, account, shop, integration, operation, grant ID and request digest. It strips the credential and routes by the independently attested stable scope digest. Public Worker fetch is still 404 and held configuration admits nothing. The WordPress fixture connector uses this class in local tests, not a production HTTP client. Real WordPress egress, transport identity issuance, approved routing, policy service, custody and key administration remain separate gates. Do not assume an Access hostname or any administrator has been approved.

If an admission write succeeds and the external floor acknowledgment is uncertain, quarantine the request. An independent operator must read both heads and their receipts, establish whether the floor advanced for the same bound grant, preserve the consumed grant, and document the verified outcome before any new admission. A stale, unavailable or divergent floor remains held. This release has no reset, resend, repair endpoint or production drain command.

## Policy, independent witness and custody service adapters

`policy-service.mjs` exports separate SQLite-backed Durable Object classes. Policy persists a pending receipt before asking the witness to compare and advance a monotonic commitment, then finalizes only on an exact acknowledgment. Witness is a private binding to a separately governed service. Bootstrap requires externally reviewed matching initial heads, with no default initialization in the service. Restart reads validate the witness commitment. STOP and revoke updates, and reserved/in-flight/finished transitions all advance the floor. An admitted but unfinished operation remains in-flight during drain. Uncertain acknowledgment fences the object. There is no reset, rearm, resend or automatic recovery route. Production repair requires independent proof of the exact pending/committed state and separately authorized reconciliation. A simultaneous rollback of both objects defeats an entirely co-restored deployment.

`custody-service.mjs` revalidates the signed typed grant through CONTRACTS, confirms exact scope and URL, resolves an opaque external credential through the provider interface, then obtains ordered begin before invoking the injected upstream. It buffers a bounded response before acknowledging finish. An uncertain failure leaves the operation in-flight. Only synthetic credentials and a synthetic upstream are accepted. The contract does not create live provider egress. The request timeout and response limits must also be enforced by the qualified external transport.

Both adapters have held defaults and no registered public route. A real deployment requires private service routing to each scope-specific object, independently controlled witness and restore administration, verified operator/session and Access assertion issuers, grant/reply key custody and rotation, and a least-privilege provider secret resolver. The test runner uses separate fixture files with one process per request. It exercises service logic rather than the Cloudflare runtime, TLS or independent administration.

`signing-service.mjs` implements role-separated WebCrypto Ed25519 signing over the already-qualified canonical PHP digest. It requires a nonextractable private key and affirmative approval of the exact payload by a pinned canonical contract service. The fixture runs the new reply signer against the WordPress verifier and unit-tests the grant signer. The actual issuer of deployed site/operator/session assertions and Access key validation/rotation remain prerequisites. The current fixture does not mint live identities or connect to a secret manager.
