# Atomic shop template-cycle capacity

Blueprint §7 table 14 requires at most N new provider production templates per cycle. Workbook AI_Launch_Model proposes template limits 8/10/12 across W1/W2/W3; these are planning proposals, not activated policies.

New candidates now require an explicit shop with an active policy containing `template_cap: {limit: 8, duration_seconds: 604800, anchor_utc: "2026-01-05 00:00:00"}`. This example is a test fixture, not runtime configuration. UTC half-open cycles are computed from the strict operator anchor and bounded duration. Callers cannot supply/reset the cycle ID or clock. Changing only the quantity limit preserves the cycle identity and existing accounting. Changing anchor/duration is an explicit policy change, never automatic rollover configuration.

A template-wide lineage lock prevents concurrent cross-shop binding of one global template ID/version. Within that boundary a nonblocking shop lock serializes the final policy read, current-cycle usage count, durable reservation and readback. Provider/AI calls are absent. Reservations are conservative: a failed subsequent template write consumes capacity; there is no automatic refund or destructive cleanup. Identical same-owner replay does not consume another slot, even after the cycle is full. Missing or different shop ownership fails closed. Historical templates without immutable reservation ownership require explicit reconciliation; no history is silently assigned or rewritten.

Accounting uses existing shop usage storage, workflow `production_template`, stage `template_prepare`, deterministic cycle `run_id`, and template fingerprint in `model_key` as the local reservation binding. This local stage is not a billable AI model record. The separate `template_capacity` read projection reports current cycle, used/remaining and no external authority. Invalid policy edits fail validation. No schema change, production policy activation, finance work or external execution occurs.
