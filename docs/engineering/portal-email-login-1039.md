# DigiForge 1.0.103.9 — email login and initial owner setup

DigiForge sign-in requests an eight-digit cryptographically generated email code through existing `wp_mail`. It expires after ten minutes, allows five verification attempts, is browser-bound and stored only as a keyed hash. Atomic compare-and-swap and deletion prevent concurrent verification/replay. Requests are bounded per IP, per email and globally; verification is additionally IP-limited. Unknown/disabled accounts and delivery failure receive account-neutral responses. A successful `wp_mail` return establishes transport acceptance only, never inbox delivery.

Verification rechecks account identity/password hash and profile generation/disablement, applies WordPress user-authentication filters and uses native WordPress session tokens/cookies plus existing DigiForge sessions. No account or authority is created by login. Pending invitations may receive a WordPress session only for their invitation return; they receive no active DigiForge session until existing audited invitation acceptance succeeds. Logout and revocation retain native/session protections. WordPress password recovery remains available; DigiForge no longer accepts password-login submissions.

Ed25519 verification is unchanged. A trusted operator can prepare the private setup bundle with `bin/prepare-portal-owner-setup.php --site=https://digiforge.converentis.com/ --output=/private/new-directory --approval=<reviewed-approval-sha256> --expires=<UTC-epoch-within-30-days>`. It refuses existing output, writes mode-0600 files in a mode-0700 directory and never prints secrets. The helper is an offline operator tool, not a production endpoint or automatic provisioning action. No real setup bundle was generated during development.

For an initial installation with no existing trust, the helper creates an internal signed authority, public host configuration and an owner-only enrollment code; the ephemeral signing key is wiped and never placed in WordPress. The trusted operator, under separate approval, must place the envelope/config outside public web access, use the correct deployed absolute path and load the configuration before the plugin. Never replace an existing trust key or authority: recover the existing custodian-signed authority instead, and provision a separately generated random enrollment-code digest and exact-site constant. Any future renewal/rekey needs trusted recovery approval; this helper is initial setup, not automatic renewal.

The owner handles only email verification and the one-time setup code. After a successful claim the code cannot be retried, including interrupted/audit-failed enrollment. Trusted recovery must inspect claim, native grant and profile audit evidence before authorizing reconciliation; do not blindly delete the claim or recreate grants. Rollback requires the matched files/database recovery checkpoint. An account-email change, password reset, disablement or authority revocation fails closed.
