## Implemented local controls

`TinyFishResearchStore` persists protected state in a dedicated, non-autoloaded WordPress option namespace; it creates no tables or migrations. It requires current explicit `personalized_pod` assignments for both `manage_digiforge` and `manage_digiforge_connections`. Four-shop architecture is unchanged; Digital/Standard POD/Jewelry are rejected by this store. Supplied scope/approval/rate hashes remain proposed offline metadata, not proof of current provider ownership or monetary authority.

- **Atomic state and audit:** require InnoDB options/audit tables. Lock current shop assignment state, compare locking and snapshot reads, reauthorize under lock, then lock the account/environment/shop ledger. Checkpoint, reservation, request ID, lease revision and append-only audit metadata commit together. Nested calls use savepoints and never implicitly commit the caller transaction. Unknown rollback/commit outcomes deny retry. Read/restore never silently initialize missing state.
- **Durable replay prevention:** validate the protected ledger MAC and complete matching retained audit history, require the current session revision and one-use request ID, and update the existing phase-1 checkpoint under the same lock. Old checkpoints cannot be submitted to this store as replacement state. A rollback of only the mutable option is detected against retained audit records. This is not external WORM storage and does not prove resistance to coordinated privileged rollback of the entire database/audit history.
- **Reservations:** integer USD micro-units; conservative full-session reservation comes from the existing contract. Account/environment/shop cap is shared across sessions and integration IDs. Caps/concurrency cannot be enlarged in-place; maximum three concurrent offline sessions, 100 stored sessions and 250 audit transitions per ledger, bounded payload size. Actual provider charges and live approved ceilings remain UNKNOWN. Expiry, revocation, lease loss and uncertain work never automatically refund reservations. There is intentionally no charge settlement, fabricated financial evidence or forced-reset interface. A future reviewed budget period/authoritative settlement design must precede live use; reserve exhaustion safely blocks.
- **Worker concurrency:** one 30-second lease per session, bounded by its original deadline. Stale revision, another active worker and expired leases cannot dispatch. A crashed worker may be replaced only before an intent was durably consumed. Advance consumes the intent/checkpoint atomically and sets `UNKNOWN_RECONCILIATION_REQUIRED`; further dispatch/profile restore is blocked even after lease expiry. No provider is actually dispatched. No synthetic success clears an ambiguous operation.
- **Bounded recovery:** only local interception/worker preflight failures are retryable, at most three recorded attempts before PAUSED. Authentication, billing and arbitrary provider failures are not accepted retry reasons. There is no automatic retry loop or live error ingestion. Revocation remains possible after expiry/uncertainty, clears the current encrypted handle/lease and retains reservation/audit history; it does not claim remote session termination or provider profile deletion.
- **Encrypted profile interface:** stores only a bounded opaque profile handle, never cookie exports, credentials, CDP URLs or raw browser state. Uses XChaCha20-Poly1305 with random nonces, scope digest as associated data and domain-separated HKDF keys; matches the repository's existing authenticated-encryption pattern. Independently supplied 32-byte key and sodium are mandatory; no plaintext fallback or managed-key creation. Ledger MAC is separately domain-separated. Restore checks current scope, authority, status and deadline, verifies audit integrity, decrypts only for a trusted internal caller and records redacted access metadata before returning. A wrong key, scope drift, expiry, revocation or missing audit denies access. No REST/frontend secret-returning endpoint is registered. Caller key custody, access and rotation need separate deployment review; no actual key is provisioned by this phase.
- **Secret protection:** serialized/debugged service objects omit/reject keys. Public state excludes profile ciphertext and worker identity; audits contain actor, scope/request/state hashes and status metadata, not profile handles, cookies, URLs with secrets, DOM or provider error text. Denied privileged operations are recorded with a fixed reason after safe rollback; failure to audit remains a denial. Ciphertext backups/MVCC retention and actual TinyFish data retention are not erased/certified by local revocation.

Server-side integration must supply the current trusted scope from existing reviewed ownership, tariff and authorization sources on every call. The store compares that full scope with the stored checkpoint; it cannot discover provider ownership drift itself without authoritative records. Offline persistence is not a general Printify/TinyFish grant, and live monetary budgets must still pass existing authoritative reservation/admission boundaries. There is no link to deferred revenue/profit or Finance implementation.

## Network interception evidence

`includes/Research/offline/tinyfish-interception.cjs` creates a fresh isolated local Playwright context with no storage state, blocked service workers and downloads disabled. It fails and closes the context if WebSocket interception or other setup cannot be installed. The first page is the only admitted top-level frame; later pages/popups are closed and cannot use the main-page admission path.

All requests are routed before navigation. Only exact bounded fixture URLs from the phase-1 public-document pattern, GET, no body, top frame of the first page and no HTTP redirect ancestry qualify. Even these requests are **fulfilled from local synthetic strings**. All other methods, origins, query variants, frames, XHR/fetch, WebSockets and targets are aborted/closed. There is no `continue`, upstream fetch or TinyFish connection. Events contain method/type/decision only, not request payloads or browser secrets.

Actual local Chromium tests exercise document admission, POST/PUT/PATCH/DELETE rejection, cross-domain and orders denial, frame rejection, WebSocket closure, extra-page isolation, service-worker non-creation, client-side unauthorized redirects, query-target denial, and fail-closed missing-interceptor cleanup. Fifteen checks observed ten intercepted HTTP requests: nine blocked and one synthetic fixture document. These are measured local events, **not TinyFish live verification**. HTTP redirects from a real upstream, remote service-worker/proxy/network escape resistance, provider-internal traffic and authenticated page behavior remain unverified. This harness cannot be substituted as a connected adapter or a remote network attestation.
