# Unified DigiForge App UX + Post-Approval Product Factory Blueprint

Status: DESIGN ONLY — NO PRODUCTION CHANGES

## 1. Executive decision

DigiForge should operate as one private application with one canonical operational home.

- Canonical application URL after implementation: `https://digiforge.converentis.com/`
- Existing `/control-center/` becomes a compatibility redirect to `/` only after tested deployment.
- WordPress `/wp-admin/` remains available for maintenance, plugin administration, recovery, and emergency access, but it is not the normal DigiForge workflow.
- Existing informational module pages should not remain parallel operational surfaces. Their useful explanatory content should be absorbed into contextual help/docs inside the unified application.
- No production change should occur until responsive UX, lifecycle state model, product-production orchestration, approvals, and migration behavior are reviewed and tested on a branch/staging path.

## 2. Current-state audit

### 2.1 Existing root homepage

The current WordPress front page is page ID 6 and acts as a public-style product/platform landing page. It links to Platform, Research, Product Factory, POD, Listings, Orders, Finance, Control Center, Safety and Docs.

This creates a second navigation system that overlaps the Operations Console.

### 2.2 Existing Operations Console

The current `/control-center/` page mounts `[digiforge_admin_portal]` and is the actual operational UI. It already includes:

- Dashboard
- Approval Inbox
- Research
- Product Factory
- Digital Products
- Production
- POD
- Listings & Etsy
- Orders & Fulfillment
- Finance & Analytics
- Integrations
- Audit Log
- System & Controls

### 2.3 Current responsive defect

The present portal shell is constrained by its surrounding WordPress page/theme layout. On tablet-size screens the application occupies a narrow centered column while large areas of viewport remain unused. This is not acceptable for a production control center.

The plugin CSS currently switches from a 250px sidebar layout to a single-column layout at 980px. That breakpoint is too aggressive for tablets and smaller laptops, and the surrounding WordPress theme can further constrain width.

### 2.4 Current post-approval behavior

Research approval and product development are separate actions.

Today:

1. Candidate is `PENDING`.
2. Human presses APPROVE.
3. Candidate becomes `APPROVED`.
4. A separate “Develop approved candidate” action invokes `Launch\ExecutionEngine::develop()`.
5. The engine promotes the candidate to an opportunity and creates:
   - product family
   - product
   - product version
   - AI-generated structured product specification
6. The engine stops with `next_action = Generate production assets and listing package; Etsy publishing remains gated.`

Actual production files, visual assets, listing graphics, mockups and release packages are not yet automatically generated by the Launch Execution Engine.

The Production domain already provides the data model and governance structure for asset specifications, plans, intents, revisions, QA and release bundles. Production intents currently support providers such as internal, AI, Canva, manual and future provider and are created in a blocked state. The missing part is the execution/orchestration layer that converts an approved product specification into actual generated assets and then drives QA/review.

## 3. Target operating model

### 3.1 One application, one shell

Normal operator journey:

`Login -> DigiForge Dashboard -> all modules inside one application shell`

The application shell should own:

- navigation
- route/view state
- global search
- approval count
- alerts
- system state
- user/session menu
- responsive behavior
- contextual breadcrumbs
- record detail drawers/panels

Do not build more standalone WordPress operational pages.

### 3.2 Authentication

Keep WordPress authentication and DigiForge capabilities. Do not build a second credential system.

- Logged-out root: sign-in screen or safe landing/sign-in gateway.
- Logged-in authorized user: unified DigiForge dashboard.
- Unauthorized WordPress user: explicit access denied.
- `/wp-admin/`: preserved for maintenance and recovery.

## 5. Responsive UX specification

### 5.1 Desktop — >= 1200px

- Full viewport application canvas.
- Persistent 240–280px left navigation.
- Main workspace uses remaining width with a max content width only for text-heavy forms, not the entire application.
- 12-column content grid.
- 3–4 dashboard cards per row depending on width.
- Approval detail can use master-detail view: queue on left, selected record on right.
- Tables remain real tables with sticky headers and horizontal overflow only when genuinely necessary.
- Optional right-side context drawer for evidence, QA or activity.

### 5.2 Tablet — 768px to 1199px

- Collapsible 72px icon rail or drawer, not a full-width stacked navigation.
- 2-column dashboard cards.
- Full available viewport width.
- Approval details in one main panel with expandable evidence.
- Action buttons remain touch-sized.
- Complex tables use reduced columns + detail drawer rather than forcing desktop width.

### 5.3 Mobile — < 768px

- Top app bar + navigation drawer.
- Single-column cards.
- Tables convert to record cards or key-value rows.
- Primary actions may use sticky bottom action bar where appropriate.
- Approve/Reject/Request Changes actions remain accessible without long horizontal scrolling.

### 5.4 Global responsive requirements

- No fixed narrow wrapper around the application.
- No theme-imposed 700/1100px content width on the operational console.
- Respect browser zoom and accessibility text scaling.
- Minimum comfortable touch target around 44px.
- Avoid hover-only interactions.
- Breakpoints must be based on usable layout, not device names alone.

## 7. Approval architecture

DigiForge should use three major human gates by default.

### Gate A — Opportunity Approval

Question: “Should DigiForge spend resources making this?”

Displays:
- research title
- summary
- score and component scores
- evidence and sources
- intended shop
- risk notes

Actions:
- Approve
- Reject
- Research Again / Needs More Research

### Gate B — Product Approval

Question: “Is the actual finished product good enough to sell?”

Displays:
- final product specification
- actual downloadable/print assets
- thumbnails/previews
- product variants
- mockups
- QA report
- file checksums/version
- estimated cost/margin where relevant

Actions:
- Approve Product
- Request Changes
- Reject Product

### Gate C — Listing / Publish Approval

Question: “Is this exactly what should appear on Etsy?”

Displays:
- listing title
- description
- tags/SEO
- price
- category/attributes
- personalization settings
- listing images/media order
- shop target
- digital files or POD bindings

Actions:
- Approve Etsy Draft
- Request Changes
- Reject Listing
- Publish (only when publish control is authorized)

## 8. Lifecycle state model

Recommended operator-visible lifecycle:

`RESEARCHING`
-> `OPPORTUNITY_REVIEW`
-> `OPPORTUNITY_APPROVED`
-> `DEVELOPING`
-> `PRODUCT_SPEC_READY`
-> `PRODUCTION_PLANNING`
-> `ASSET_GENERATION`
-> `ASSET_QA`
-> `PRODUCT_REVIEW`
-> `PRODUCT_APPROVED`
-> `LISTING_BUILD`
-> `LISTING_REVIEW`
-> `LISTING_APPROVED`
-> `ETSY_DRAFT`
-> `READY_TO_PUBLISH`
-> `LIVE`

Exception states should include:

- NEEDS_RESEARCH
- NEEDS_CHANGES
- BLOCKED
- FAILED
- REJECTED
- PAUSED

The dashboard and record detail should always show the current stage, next action, blocking reason and latest audit event.

## 9. Post-approval Product Factory orchestration

### 9.1 After Opportunity Approval

Approval should enqueue/start product development when the architecture is completed, instead of requiring an unexplained separate action.

Safe target behavior:

1. Research candidate approved.
2. Create/promote opportunity.
3. Run AI product-development specification.
4. Create product family, product and version.
5. Persist structured requirements.
6. Create production plan.
7. Create required asset specifications.
8. Create production intents for each asset.
9. Execute asset-generation workers.
10. Persist generated revisions.
11. Run deterministic + AI-assisted QA.
12. Build release bundle.
13. Present complete product in Product Approval.

Every stage must be idempotent and auditable.

### 9.2 Digital-product production path

For DigiCraftifyDigital, Product Factory should be able to generate a bundle such as:

- customer-facing PDF(s)
- PNG/JPG supporting files where needed
- editable template artifacts where supported
- instructions/readme
- language/localization variants
- ZIP packaging
- preview images
- listing graphics

For Canva-dependent editable products, DigiForge should support a provider-specific production intent rather than pretending a Canva edit link can be generated from a local PDF alone.

### 9.3 POD production path

For DigiCraftifyGoods:

- print artwork
- required size/aspect/bleed variants
- personalization schema
- Printify/Gelato-compatible production files
- product mockups
- cost snapshot
- margin validation
- provider mapping
- QA

No provider submission occurs until POD controls are authorized and the relevant readiness gate passes.

## 10. Product images and visual assets

Two asset classes must remain separate.

### A. Product/production assets

What the customer receives or what the POD provider prints.

Examples:
- PDF planner
- PNG artwork
- SVG where supported
- spreadsheet/template file
- print-ready artwork

### B. Marketing/listing assets

What Etsy shoppers see.

Examples:
- hero thumbnail
- lifestyle/mockup image
- what-is-included graphic
- feature/benefit slides
- dimensions/formats graphic
- personalization explanation image
- language/variant image
- instructions/how-it-works image

The database and production plan should explicitly identify asset purpose so a listing mockup can never be confused with a print/download deliverable.

## 12. Technical implementation plan

### Phase U1 — Read-only architecture lock

- Preserve current production behavior.
- Keep Candidate #1 pending.
- Document current pages, routes, controls and data model.
- No redirects, homepage changes or automation changes.

### Phase U2 — Unified App Shell on branch/staging

- Decouple app shell from WordPress theme width.
- Build full-width responsive shell.
- Add desktop/tablet/mobile navigation behavior.
- Add global status bar and breadcrumbs.
- Keep existing module data/actions unchanged initially.

### Phase U3 — Unified approval inbox

Aggregate approval sources into one inbox with type filters:
- Research
- Product
- Production QA
- POD
- Listing
- Fulfillment

### Phase U4 — Product production orchestrator

Build the missing orchestrator between `ExecutionEngine::develop()` and existing Production repository primitives.

Required services:
- ProductionPlanner
- AssetSpecFactory
- ProductionIntentDispatcher
- AssetGenerator adapters
- RevisionRecorder
- QaRunner
- ReleaseBundleBuilder

### Phase U5 — Visual generation layer

Add provider adapters for actual product and marketing image generation. The adapter model should allow different providers without changing workflow state logic.

### Phase U6 — Listing Factory orchestration

Convert approved release bundle into:
- listing copy
- SEO/tag package
- media ordering
- pricing recommendation
- digital file binding or POD binding
- Etsy draft intent

### Phase U7 — Staging acceptance

Test:
- desktop widths including 1366/1440/1920
- tablet portrait/landscape
- mobile widths
- authentication
- authorization
- CSRF/nonces
- approval idempotency
- failed AI/provider calls
- recovery/resume
- no unauthorized external side effects

### Phase U8 — Production migration only after explicit approval

- Make unified app the front page.
- Redirect `/control-center/` to `/`.
- Remove old operational navigation paths from normal UX.
- Keep legal/contact/docs pages as needed.
- Preserve `/wp-admin/` maintenance access.

## 13. Acceptance criteria before production

Do not deploy the unified architecture until all are true:

- Desktop uses available viewport width appropriately.
- Tablet no longer looks like a centered phone UI.
- Mobile remains usable by touch.
- Root and Control Center no longer represent two competing applications in staging.
- All existing approval/research data remains accessible.
- Candidate #1 remains intact and pending until deliberately approved.
- Product development can create a product spec deterministically after approval.
- Production orchestrator can build and track actual assets.
- Actual assets and marketing/listing images are represented separately.
- QA can block progression.
- Product Approval exists before Listing Build progresses.
- Listing Approval exists before Etsy publish.
- Etsy, Printify/Gelato, order and finance side effects remain controlled by existing switches and approval gates.
- Audit events exist for every material transition.
- GitHub Engineering & Safety Audit passes.

## 14. Migration policy

The existing public-style homepage and module pages should not be deleted first. They remain unchanged until the new app passes staging acceptance. At production cutover, redirects or archival decisions are made deliberately so rollback remains possible.
