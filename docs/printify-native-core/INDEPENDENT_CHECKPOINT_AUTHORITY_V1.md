# Independent checkpoint authority interface 1.0.0

Status: PROPOSED / NOT DEPLOYED / NOT QUALIFIED. This document creates no operational authorization, trust root, credential, service, policy exception or installed configuration. Canonical native port v1 bytes and requirements remain unchanged.

## Trust boundary and platform

Recommended first qualification target: a Cloudflare Worker owning final provider dispatch, SQLite-backed Durable Object state, and a recovery witness outside the dispatcher's restoration AND administrative domain. This is a recommendation, not provisioning approval. A second namespace or service under the same administrator is not an independent witness. A VPS similarly needs a separate witness and restoration controls; one database plus backups is insufficient. Supported rollback/administrator assumptions must be explicitly approved before certification. Account entitlement, durable storage guarantees, billing and costs are unverified; no paid subscription or resources are authorized.

The independent authority must own monotonically advancing generations and the actual dispatch admission. WordPress may request preparation but never receive a Boolean permit enabling a direct provider sender. A restored WordPress key cannot issue owner grants, restore consumed requests, change roots or reset generations. No WordPress/database counter or content hash may substitute for an independently supplied epoch.

## Versioned authenticated messages

Domain separator: DF_INDEPENDENT_CHECKPOINT_AUTHORITY_1. Encoding: exact UTF-8 canonical JSON, integer timestamps, no duplicate keys, unknown fields or arbitrary endpoints; authenticate the exact bytes. Ed25519 is the proposed fixed signature algorithm; the verification library and purpose-bound trust configuration must receive independent review. There is no caller-selected algorithm. Root public keys are pinned by purpose, authority ID, key ID and monotonic root-set revision in an independently controlled verifier. Untrusted response keys, restored options or self-signed root updates are never trusted. Private issuer/workload credentials remain outside WordPress and backups; no key is created by this proposal.

Every request binds protocol version, RPC method, message purpose, authority identity, installation identity, verified owner identity, fresh independent owner-proof reference, dispatcher workload identity, deployment digest/compatibility floor, physical provider account, integration, credential reference, shop, provider name, environment, shop key, one-use request ID, fresh challenge and an exact method-specific body. Operation admission binds immutable operation/payload references, current/expected product versions and current approval/policy revisions. Signatures are not reusable across methods or purposes. Every authenticated response echoes those bindings, authority/key/root-set identity, independently issued epoch, checkpoint epoch, monotonic generation, recovery revision, issuance/expiry times, request disposition and signed evidence reference. Native responses may carry matching epochs only after the verifier has established their provenance, currentness and exact binding; string equality alone is insufficient. A separately authenticated witness attestation must bind witness identity/head/sequence to the exact epoch, generation, deployment/physical workload and challenge. Its root is pinned independently; an issuer-provided key or unsupported witness-currentness assertion is insufficient. Unknown account/credential association denies.

RPC methods: currentCheckpoint, admitOperation, requestEmergency, readDrain, recoverInstallation and rotateRoot. Emergency requests use separately approved emergency authority and never require an unrevoked mutation grant. Recovery and root rotation require independently approved out-of-band evidence; an old signing key alone cannot authorize its own replacement. Each method body has the required fields inventoried in the JSON contract. Fixed method schemas and issuer signatures are required before implementation; no arbitrary HTTP proxy or caller credential field. The accompanying JSON contract inventories mandatory fields and invariants. This proposal is not a production client.

## Issuance, revocation and dispatch

An epoch is supplied by the independently governed authority and recorded in its witness, never generated by the WordPress caller. A request is admitted only against the current witnessed generation, fresh independently authorized owner grant, current policy/approval/product versions, exact physical binding and compatible dispatcher code. Authority is short-lived (maximum 300 seconds); each operation admission additionally uses a fresh challenge and one-use persistent slot. No cached fallback on outages, no silent renewal, no automatic rearm, no automatic retry. Scalar bounds, method-specific fields, canonical encoding and replay constraints are inventoried in the JSON contract.

Every emergency event must durably advance or invalidate the generation even when STOP ALL is already true. Admission closes before acknowledgement. The final sender checks current generation before credential use and again at the actual outbound dispatch boundary. It persists the lease before network activity; provider calls never run inside retryable storage transactions. Emergency acknowledgement waits for admitted leases to drain. In-flight uncertainty remains UNKNOWN and consumed; timeout never frees a slot. Failed persistence or unknown drain state cannot produce a successful acknowledgement.

Ordinary provider workflows remain under existing STOP ALL, external safety lock, owner/approval and activation controls. Release-held native core calls continue to deny until separately qualified policy, installation, root, binding, custody and operational authorizations exist. Read-only local diagnostics issue none of these permissions.

## Rollback and recovery

Check state against the independent witness on restart, point-in-time restore, namespace replacement, root changes and deployment rollback. Stale epoch, generation, root-set revision, identity or deployment floor requires recovery and denial. A recovered service must not bootstrap itself from a fresh local generation or ignore outstanding leases. Recovery requires independently approved reconciliation of witness history, consumed slots and pending operations. Revoke earlier authority and verify credential invalidation before any separately approved rearm. Maintain the all-root rollback counterexample unless the supported external boundary actually prevents it; synthetic tests alone do not qualify hosted durability.

## Credential custody and evidence

The future final dispatcher must exclusively hold usable provider credentials. Previously usable Hostinger-held credentials must be independently revoked/invalidated; restored backups must not revive direct provider access. There is no direct-provider fallback or generic proxy. A restored sender that retains a usable provider token could bypass a cooperative witness callback: code-digest claims and signatures alone do not prevent this. The independent boundary must control the actual final sender/credential admission, or independently enforce credential invalidation and code/restoration constraints. Until such mandatory enforcement is demonstrated, the Cloudflare-plus-witness proposal remains RECOVERY_BLOCKED. Secret administration, rotation, migration and recovery require separate approval and audit. None is performed here.

Receipts contain only bound non-secret IDs, minimized field observations, state, generation and signed evidence hashes; omit credentials, cookies, nonce values, buyer PII and raw provider payloads. Receipt authenticity comes from the trusted issuer/store, not a caller's self-hash.

## Qualification gates

Require tests for WordPress/filesystem/database rollback; dispatcher/code/namespace rollback; authority outage/partition; independent witness failure and coordinated-root rollback; stale root/deployment/workload identity; wrong shop/account/credential; nonce replay and concurrent slot consumption; lost commit acknowledgement; emergency before/during/after dispatch; pending drain and restart; expiry/revocation; provider timeout and uncertain outcome; credential duplication and restoration. No hosted durability, exclusive custody or live acceptance is certified by local fixtures.
