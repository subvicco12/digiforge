# Independently reviewed local mutation-source association

`NativeBusinessMutationAssociation` v1.0.0 prepares and independently reviews the exact current business product/version, provider mapping, asset specification, artwork, package, sealed IMAGE_UPLOAD plan and its original reviewed policy. It reuses the existing `ReviewedLocalEvidence` policy stream, its distinct author/reviewer checks, transaction, audit integrity, revision CAS, revocation and expiry. It creates no credential store, shop mapping, dispatcher or execution authority.

The stable stream key is `native-mutation-source:` plus the canonical hash of shop key, integration, provider shop, environment and business product ID. The reviewed payload is actor-independent; each observer must independently satisfy current signed shop/module/session authority. Exact source dependencies, the core wire fingerprint and original plan-policy revision are frozen in the payload. Sharing an artwork hash does not approve another business product or plan.

Current-session/shop/module authorization precedes the provisional mapping-to-product lookup. That raw identity only locates the reviewed stream; it never authenticates the source or leaves the service without a successful full source join. Identical approval and producer receipts bracket one full current-source scan. `NativeBusinessMutationEvidence::sourceMaterial` reuses the final dependency hashes already computed by the original resolver while preserving every original pre/post validation and the public resolve1.0 response. There is no cache. `current_source_evidence_hash` binds the current observer's exact validated source. The descriptor compares that hash and independently hashes the sealed wire body before a final association revalidation.

`source(scope, actor, mapping, spec, plan)` returns schema `DF_NATIVE_MUTATION_ASSOCIATION_SOURCE_1` and its source_hash. `propose(..., expectedSourceHash, expectedReviewRevision, effectiveAt, expiresAt, requestId)` registers that exact payload in the existing review system. `decide(..., expectedReviewRevision, proposalHash, decision, requestId)` requires a distinct reviewer. `read(...)` returns the exact currently approved association only after current source and review revalidation.

The monotonically increasing `association_version` is the existing reviewed stream's proposal version. `review_revision` is its transition revision. Neither is a business row ID, provider product version, independent recovery epoch or currently verified canonical native mutation counter. `native_product_version` remains null. Ordinary source resolvers retain their transaction guards.

The decision uses the existing review transaction's condition callback. It verifies the same database object/physical connection and calls `NativeBusinessEvidence::lockCurrent`. This additive verifier requires an active caller-owned REPEATABLE READ transaction, autocommit1, strict InnoDB durability and real tables. It locks actual business, product/version, mapping/ownership, production and approval-event rows/ranges, compares all15 frozen whole-row dependency hashes and rechecks current authority. It never commits or rolls back the caller's transaction. Independent concurrent product updates, new ownership rows and newer approval events are tested to time out until the caller releases these locks.

A minimized `native_mutation_business_source_reviewed` audit receipt commits in that same existing review transaction. Association reads require exactly one matching producer receipt, exact source/proposal/review revision and the actual reviewer actor. An otherwise valid generic policy approval cannot impersonate this producer. Receipt substitution, missing or conflicting receipts deny.

Both historical principals must still hold every source module capability through the current shop authorization service. Their old WordPress sessions need not remain alive; the current observer separately requires its own authenticated session. The producer receipt also binds the shop-assignment ledger revision captured under the existing review transaction's ACL lock. Any assignment ledger change, including revoke/regrant, invalidates the old association approval and requires a new explicit review. This deliberately fails closed even for an unrelated assignment change in the same shop. This does not certify atomic protection of every WordPress role, session or independent authority root.

`business_dependency_cas_verified=true` describes only these business-table locks and producer provenance. It does not claim an atomic join of every artwork/package/supplier option and session/provider identity root. Current full source and review checks surround persistence and are repeated on every read. `source_approval_cas_verified` therefore remains false; full lock-aware artifact and authority source verification is an additional software requirement.

The local association's `business_package_binding_approved=true` means only that distinct current principals reviewed the exact frozen source payload. `mutation_authorized`, `dispatch_permitted`, `native_version_counters_verified`, `companion_payload_equivalence_verified`, `independent_checkpoint_verified` and `external_execution_authorized` remain false. Canonical mutation capabilities are not advertised. STOP ALL, external lock and RELEASE HOLD remain unchanged.

## Bounded upload wire observation

`uploadDescriptor(scope, actor, mapping, spec, plan, expectedSourceEvidenceHash)` requires the current approved association and exact current `NativeBusinessMutationEvidence` hash. It returns schema `DF_NATIVE_IMAGE_UPLOAD_WIRE_1`, version, scope fingerprint, actor, source evidence hash, plan/package hashes, decoded asset SHA-256, exact sealed file_name, fixed POST `/v1/uploads/images.json`, core payload fingerprint and descriptor hash. It returns no asset bytes, contents, raw provider body or credentials. The descriptor does not authorize POST or provider dispatch.

The existing core filename is `shop2-` + the first16 package-hash characters + `.png`. A companion may prepare a NEW unapproved intent using this exact request and independently compare the full canonical wire fingerprint. It must never rewrite an already approved intent. Core-side approved source equality does not itself establish companion payload equality. Asset/account duplicate protection must survive a naming change; the product/version HELD candidate key is not a global physical-asset upload deduplication guarantee.

## Remaining native software

Canonical source/approval row locking, approved mutation admission, canonical version counters, final one-shot reservation, trusted terminal receipt import, publication lifecycle/channel joins, order allocation and recovery still require their actual producers and exact-contract tests. No mock epoch or false approval is substituted. Independent rollback resistance and exclusive credential custody remain separate unqualified operational/security boundaries.
