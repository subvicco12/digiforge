# DigiForge v1.0.66 Controlled Deployment Plan

## Certified candidate
- Candidate: DigiForge 1.0.66
- Expected schema after migration: 22
- Exact-head certification must come from the Engineering & Safety Audit artifact whose manifest commit equals its audited candidate head.
- Production currently remains 1.0.65. Never infer its database schema from the candidate; read production immediately before change.

## Hard pre-install gates
Deployment is BLOCKED unless every item is evidenced immediately before installation:
1. `/digiforge/v1/health` reports the expected currently deployed version and `externally_locked=true`.
2. `/digiforge/v1/readiness` reports STOP ALL active, activation not authorized, automation unarmed, no effective consequential feature switches, and queue query verified.
3. A fresh, retrievable full production database backup exists. Record provider identifier/location, UTC timestamp, size where available, and integrity evidence.
4. The audited rollback plugin for the currently deployed release is retrievable and its recorded checksum verifies.
5. The v1.0.66 install ZIP checksum verifies and its release manifest says plugin 1.0.66, schema 22, exact audited commit, `external_actions_performed=false`, and `production_activation_authorized=false`.
6. Recovery/restore instructions are available. Evidence flags alone are not proof.
7. No unresolved UNKNOWN external mutation is converted into retry permission by deployment.

Historical `external_actions_performed=true` evidence is not a deployment failure by itself and MUST NOT be cleared or rewritten. The deployment gate concerns current external lock state and preservation of historical evidence.

## Migration boundary
The upgrade is additive from the production-reported schema to schema 22. Do not manually set schema-version options. WordPress/DigiForge migrations must advance the schema. If migration does not finish at current=expected=22, STOP and restore the compatible audited plugin/database pair.

Before install retain:
- production version and current/expected schema
- readiness evidence hash
- recovery evidence hash
- queue health/expired leases
- current effective switches
- audit health

After install, before any capability release, verify:
- plugin version 1.0.66
- schema current=expected=22
- STOP ALL ON
- activation authorization OFF
- automation armed FALSE
- every consequential effective switch FALSE
- queue query healthy and no expired leases
- audit healthy
- no new external mutation caused by install/migration
- provenance/integrity/persistence evidence remains readable

## Abort and rollback
Abort immediately on migration error, unexpected effective capability, missing table, audit failure, queue corruption, checksum/manifest mismatch, or any unexpected external mutation.

Rollback means restore the last compatible audited plugin + database checkpoint together. Do not downgrade plugin code over a schema-22 database and assume compatibility. Do not delete historical operation, integrity, acknowledgement, persistence, or audit evidence to make readiness pass.

## Production smoke
Only after installation and post-install lock verification may the internal smoke plan run. It remains local/internal and must not call Etsy, Printify, Gelato, OpenAI, fulfillment, finance/tax filing, or any external mutation endpoint.

Therefore installation is BLOCKED until the protected pre-release posture is explicitly restored and re-verified. No deployment action is authorized by this document.
