# DigiForge v1.0.86 Controlled Deployment Plan

## Certified candidate

This candidate releases the governed approved-SVG-to-PNG orchestration added after v1.0.85. It can derive a separate listing-image PNG asset revision only from an APPROVED SVG revision whose protected source bytes match the recorded checksum. The derived revision begins PENDING_QA, records immutable source provenance, does not inherit source approval, does not mutate an existing release bundle, and performs no Etsy or other external action. Deterministic PNG QA support is included. Installation itself grants no listing-media approval, Etsy attachment authority, publication authority, or POD production authority.

- Candidate: DigiForge 1.0.86.
- Expected schema after migration: 23.
- Install only an Engineering & Safety Audit artifact whose release manifest commit equals the exact audited candidate head.
- Read production immediately before change; never infer its installed version or schema from repository state.

## Hard pre-install gates

Deployment is BLOCKED unless all are evidenced immediately before installation:
1. Health/readiness show the currently installed release and the operator records the current STOP ALL / activation / automation posture; do not silently change an already-authorized production posture merely to install this code-only release.
2. Existing capability authorization and effective-switch state is captured before installation and must be preserved unless a separately governed safety action requires revocation.
3. A fresh retrievable production database backup has concrete identity, location, capture time and fresh verification evidence.
4. The rollback plugin/database checkpoint is retrievable and compatible.
5. The v1.0.86 ZIP checksum and release manifest verify plugin 1.0.86, schema 23, the exact audited commit, external_actions_performed=false and production_activation_authorized=false.
6. Restore instructions are available.
7. Queue/audit health is verified and no unresolved UNKNOWN is converted into retry permission.

Historical external-action evidence MUST NOT be cleared or rewritten to make readiness pass.

## Migration boundary

Do not manually set schema-version options. DigiForge migrations must leave the production-reported schema at current=expected=23. Existing integration coverage exercises historical upgrades including v21→v22 and v22→v23, missing-v23-table repair and reactivation idempotence.

Abort on migration error, unexpected effective capability, missing table, audit failure, queue corruption, checksum/manifest mismatch, or unexpected external mutation. Rollback means restoring the last compatible audited plugin + database checkpoint together.

## Post-install locked verification

Verify plugin 1.0.86, schema current=expected=23, the pre-install STOP ALL / activation / automation / effective-switch posture is preserved, queue/audit remain healthy, provenance/integrity/persistence evidence remains readable, and no external mutation was caused by install/migration.

## Governed derived-media boundary

After successful deployment, an approved Product #25 SVG may be selected as source for one local PNG derivative. The source revision/checksum must be recorded exactly. The derived PNG must remain PENDING_QA until deterministic QA completes. QA success does not constitute human approval. The derived revision must receive the required explicit human approval before it may become authoritative listing media. Creating or approving a derivative must not silently replace an approved release-bundle manifest; if authoritative release/listing evidence changes, rebuild and reapprove the affected governed evidence rather than reusing stale hashes or approvals.

## Etsy execution boundary

Installation and local raster derivation do not attach an Etsy image and do not publish a listing. Controlled ATTACH_IMAGE may occur only after the derived revision is QA-passed, explicitly approved, and the authoritative Listing #1/package/release evidence is revalidated. Use a fresh idempotency key. If the attachment result is UNKNOWN, reconcile before retry. Never repeat confirmed-success CREATE_DRAFT operation #2 or UPLOAD_FILE operation #6.

Only after ATTACH_IMAGE is CONFIRMED_SUCCESS may the already-authorized Listing #1 publish be retried, using a new idempotency key and the authoritative confirmed Etsy draft identity. Failed publish operation #7 is historical evidence and must not be rewritten or reused as success.

## Production smoke

Only after post-install verification may local/internal smoke checks run. They must not publish Etsy listings, submit POD production, move money, file tax, or turn UNKNOWN evidence into retry authority.

## Completion boundary

Successful controlled deployment proves the certified v1.0.86 code/artifact is installed without changing existing capability authority. It enables the governed local derivative workflow but does not itself approve media or authorize any new external action.
