# DigiForge v1.0.88 Controlled Deployment Plan

Candidate: DigiForge 1.0.88  
Database schema: 23

## Purpose

Release the audited governed revision-approval execution capability required by connected production operations. The capability is intentionally local and narrow: it can approve only an exact production revision already in QA_PASSED state, bound to the caller-supplied SHA-256 checksum and an idempotent operation key.

## Authority and safety boundaries

- Installation does not authorize production activation or any external action.
- Existing production STOP ALL, activation, automation, capability-switch, credential, shop-isolation, and external-action evidence must be preserved.
- Historical external-action evidence must be preserved and must never be cleared from production by the release artifact.
- The new revision approval route performs no Etsy, POD, payment, tax, GST, fulfillment, publication, media-upload, or provider mutation.
- Generic production state mutations retain their existing Idempotency-Key header contract.
- Revision approval requires an authenticated operator with manage_digiforge_production capability.
- The target revision must still be QA_PASSED at execution time.
- The supplied checksum must exactly match the persisted revision checksum.
- Approval uses the existing production lifecycle transition and append-only audit event.
- Approval does not mutate a release bundle, listing, Etsy intent, publication authority, or external-operation ledger.
- Product #25 revision #489 may be approved only against checksum 5d00d8b5feda2ff0f61091d6ea21280f525fad197b40eff18000e797c224b728 after production is verified to match the approved evidence.
- Listing #1 media/readiness must be revalidated after revision approval and before any Etsy image attachment.
- Any changed exact publication payload/readiness hash must satisfy the applicable human Gate 3 approval before publication.
- CREATE_DRAFT operation #2 and UPLOAD_FILE operation #6 are confirmed-success historical operations and must never be repeated.
- Failed publish operation #7 remains immutable historical evidence and must never be reused.
- Any future ATTACH_IMAGE or publish retry must use a fresh governed operation/idempotency key; UNKNOWN must reconcile before retry.
- No POD production, GST activation, or Gelato activation is authorized by this release.

## Certified artifact deployment

Deploy only the exact installable plugin ZIP produced by the successful Engineering & Safety Audit for the final release branch head. Do not rebuild the ZIP locally. Verify the release manifest commit SHA, plugin version, database schema version, inner ZIP SHA-256, and package boundaries before installation.

Before installation, retain a retrievable production database backup and a compatible plugin rollback package/checkpoint. Existing recovery and historical evidence must be preserved.

After installation verify:

1. DigiForge is active and reports version 1.0.88.
2. Database schema remains 23.
3. /digiforge/v1/health is OK.
4. Production activation, automation, STOP ALL and effective capability switches are unchanged from the pre-install state.
5. Historical external_actions_performed evidence remains intact.
6. Product #25 revision #489 remains unchanged unless the separately authorized approval operation is deliberately executed.
7. No external Etsy/POD action occurred as a consequence of installation.

## Release certification and fail-closed migration contract

Expected schema after migration: 23.

The current STOP ALL / activation / automation posture must be preserved exactly through deployment. Historical external-action evidence MUST NOT be cleared or rewritten. Do not manually set schema-version options; schema state must be established only by the audited plugin migration/runtime path.

A compatible rollback means restoring the last compatible audited plugin + database checkpoint together. Deployment is BLOCKED if the exact audited artifact, manifest/checksum binding, retrievable database backup, compatible rollback checkpoint, or pre-install production posture cannot be verified.

The connected-execution body-key exception applies only to this local raster-and-QA workflow. Existing mutation routes retain their required `Idempotency-Key` header contracts. The v1.0.88 revision-approval route is a separately bounded local approval operation and does not relax those existing contracts. QA success is not human approval; revision #489 may transition to APPROVED only because the user supplied separate explicit approval and the runtime revalidates the exact QA-passed checksum at execution time.

## Post-deployment governed continuation

Only after the installed runtime is verified may the already explicit human approval for revision #489 be executed through the governed revision-approval endpoint with a fresh operation key and the exact approved checksum. Re-read the revision immediately before mutation and verify QA_PASSED plus checksum equality. After approval, re-read durable audit/state evidence before proceeding to listing-media readiness work.
