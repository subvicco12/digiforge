# DigiForge v1.0.82 Controlled Deployment Plan

## Certified candidate

This candidate adds the governed live-site human decision surface for persisted PENDING Gate 3 listing-readiness reviews. The surface validates persisted readiness JSON, its SHA-256 evidence hash, required SEO/media/POD prerequisites and REVIEW_REQUIRED listing state before rendering decision controls, and routes an explicit operator decision through the existing transactional review-decision path. Installation itself makes no review decision and performs no external execution. Recovery evidence and database schema remain v23.
- Candidate: DigiForge 1.0.82.
- Expected schema after migration: 23.
- Install only an Engineering & Safety Audit artifact whose release manifest commit equals the exact audited candidate head.
- Read production immediately before change; never infer its installed version or schema from repository state.

## Hard pre-install gates
Deployment is BLOCKED unless all are evidenced immediately before installation:
1. Health/readiness show the currently installed release and the operator records the current STOP ALL / activation / automation posture; do not silently change an already-authorized production posture merely to install this code-only release.
2. Existing capability authorization and effective-switch state is captured before installation and must be preserved unless a separately governed safety action requires revocation.
3. A fresh retrievable production database backup has concrete identity, location, capture time and fresh verification evidence.
4. The rollback plugin/database checkpoint is retrievable and compatible.
5. The v1.0.82 ZIP checksum and release manifest verify plugin 1.0.82, schema 23, the exact audited commit, external_actions_performed=false and production_activation_authorized=false.
6. Restore instructions are available.
7. Queue/audit health is verified and no unresolved UNKNOWN is converted into retry permission.

Historical external-action evidence MUST NOT be cleared or rewritten to make readiness pass.

## Migration boundary
Do not manually set schema-version options. DigiForge migrations must advance the production-reported schema to current=expected=23. Existing integration coverage exercises historical upgrades including v21→v22 and v22→v23, missing-v23-table repair and reactivation idempotence.

Abort on migration error, unexpected effective capability, missing table, audit failure, queue corruption, checksum/manifest mismatch, or unexpected external mutation. Rollback means restoring the last compatible audited plugin + database checkpoint together.

## Post-install locked verification
Verify plugin 1.0.82, schema current=expected=23, the pre-install STOP ALL / activation / automation / effective-switch posture is preserved, queue/audit remain healthy, provenance/integrity/persistence evidence remains readable, and no external mutation was caused by install/migration.

## Production smoke
Only after locked post-install verification may local/internal smoke checks run. They must not publish Etsy listings, submit POD production, move money, file tax, or turn UNKNOWN evidence into retry authority.

## Completion boundary
Successful controlled deployment proves the certified code/artifact is installed without changing existing capability authority. It does not grant any new integration or automation authority. Any PENDING Gate 3 review remains undecided after deployment. Approve/Reject requires an explicit human decision in the governed Listings workflow and is separate from Etsy publishing or any other external execution.
