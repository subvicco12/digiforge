# DigiForge v1.0.94 Controlled Deployment Plan

Candidate: DigiForge 1.0.94
Expected schema after migration: 23

## Purpose
v1.0.94 adds a governed terminal supersession path for an irrecoverably stale, already-reconciled staging recovery operation whose exact planned plugin version can no longer be verified because isolated staging now runs the current verified release.

## Safety invariants
- Preserve current STOP ALL / activation / automation posture.
- Supersession requires STOP ALL, the durable safety lock, an authenticated human operator, exact confirmation, an already reconciled staging-only restore, no immutable verification receipt, healthy locked staging, and proof that staging runs the different current verified recovery package.
- Historical operation claims and supersession receipts are immutable and must be preserved. They are never deleted or rewritten.
- Historical external-action evidence MUST NOT be cleared or rewritten.
- The superseded operation remains non-replayable and grants no retry, provider execution, commerce execution, Etsy publish, POD production, fulfillment, money movement, tax, or GST authority.
- The global recovery slot advances only through an atomic compare-and-swap from the exact terminal supersession marker. A new operation still requires its own verified artifacts, backup identity binding, plan and explicit execution authorization.
- UNKNOWN or persistence failure remains reconciliation-required and fail closed.
- Production is never a recovery target.
- Do not manually set schema-version options. Schema state must come only from the audited plugin migration path.

## Fail-closed deployment contract
- Deployment is BLOCKED if artifact/checksum/manifest binding, backup, rollback checkpoint, or pre-install posture cannot be verified.
- The body-key exception applies only to this local raster-and-QA workflow; Existing mutation routes retain their required `Idempotency-Key` header contracts.
- QA success is not human approval. Human review never implies Etsy publish, provider production, fulfillment, refund, money movement, or tax filing authority.

## Release certification
Install only the exact package produced by a successful exact-head Engineering & Safety Audit. Verify manifest commit binding, plugin version 1.0.94, schema 23, package SHA-256 and ZIP integrity before installation.

## Rollback
If rollback is required, use only a compatible audited release by restoring the last compatible audited plugin + database checkpoint together. Never mix an older plugin with a newer schema or manually edit version markers.

## Post-install
Verify health, schema 23/23, STOP ALL ON, external lock ON, activation unauthorized, automation unarmed, all consequential effective switches OFF, queue health and absence of expired running leases. Supersession itself does not authorize a new destructive restore.
